# Changelog

Все значимые изменения takeAway фиксируются в этом файле.

Формат — [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), версионирование — [SemVer](https://semver.org/) с pre-`1.0` соглашением: minor — milestone-фичи и крупные треки, patch — bugfix и доработки.

## Процесс

- При мерже PR с пользовательским эффектом — добавлять строку в `[Unreleased]` под нужной категорией (`Added` / `Changed` / `Deprecated` / `Removed` / `Fixed` / `Security` / `Infra` / `Docs`).
- При выпуске релиза (тег `vX.Y.Z`) — переименовывать `[Unreleased]` в `[X.Y.Z] — YYYY-MM-DD` и заводить новый пустой `[Unreleased]`.
- Краткие, ориентированные на пользователя/оператора формулировки, без ссылок на внутренние модули. Ссылку на PR в скобках в конце строки: `(#NNN)`.
- При значимом изменении модели данных, API или стека — параллельно обновлять `01_TECHNICAL_SPEC.md` (правило в `CLAUDE.md` и в auto-memory).

## [Unreleased]

### Infra

- **CI для мобильного приложения** — отдельный workflow `Mobile`: формат, анализатор, тесты приложения и клиента API, проверка, что сгенерированные модели не отстали от исходников, и сборка release-APK (артефакт для тестировщиков, подписан debug-ключом). Запускается только при изменениях в `apps/mobile` и `libs/api-client-dart`, так что остальному CI не мешает.
- **Локальный MinIO поднимается сам вместе с бакетом.** Образ `minio/minio` перестал скачиваться, а бакет `takeaway-dev` нужно было создавать руками — без него любая загрузка картинки в dev падала. Compose берёт образ с quay.io и создаёт публичный бакет отдельным init-контейнером.
- **Официальные Angular agent skills подключены к репозиторию.** `angular-developer` и `angular-new-app` из [angular/skills](https://github.com/angular/skills) лежат в `.claude/skills/` и закоммичены, а не ставятся каждым разработчиком у себя: так их одинаково видят и облачные сессии, и локальные запуски агента, и ревью видит, какая версия скилов действует. `.claude/` целиком оставался в `.gitignore` вместе с локальным состоянием агента — теперь под контролем версий только `.claude/skills/`. Обновление — `pnpm skills:update`, источник и хеши зафиксированы в `skills-lock.json`; prettier эти файлы не трогает, чтобы дифф при обновлении показывал изменения апстрима, а не переформатирование.
- **Автодеплой снова работает.** В workflow был захардкожен `HOST: 62.238.4.92` — адрес выведенного из эксплуатации сервера, который провайдер с тех пор переназначил кому-то другому. Триггер при этом стоял на `main`, а прод собирается с `infra/migrate-takeaway-md`, так что деплой не запускался вовсе, а запущенный вручную полез бы с боевым ключом на чужую машину. Хост переехал в секрет `DEPLOY_HOST`, ветка — в одну переменную наверху файла, host-key проверяется до подключения с явным указанием, что чинить его через `ssh-keyscan` по IP нельзя: keyscan доверяет тому, кто ответил, и это ровно тот сценарий, который здесь уже случился.
- **Деплой перестал считать успехом невыехавшую сборку.** Гейт спрашивал только «ответил ли кто-нибудь 200». Контейнер, который не перезапустился, продолжал отдавать прошлый билд — и деплой рапортовал успех. Теперь `/api/health` возвращает коммит сборки, и workflow ждёт именно тот, что задеплоен; отдельно проверяется `/api/health/ready`, чтобы миграция, оставившая базу недоступной, роняла деплой, а не уезжала в прод молча.
- **Перезагрузка edge-nginx больше не теряется молча.** `deploy.sh` дёргал edge через compose-файл соседнего проекта и глушил результат в `|| true`. Когда тот репозиторий переехал, reload перестал происходить вообще: edge держал адрес пересозданного `takeaway-nginx-1`, и все домены отдавали 502 — симптом, который выглядит как что угодно, только не как пропущенный reload. Добавлен прямой fallback `docker exec edge-nginx nginx -s reload` и громкое предупреждение, если не сработал ни один путь.
- **Имя edge-контейнера больше не угадывается.** Наш fallback звал `edge-nginx`, а в runbook соседнего проекта тот же контейнер называется `rayn-prod-nginx-1` — вероятно, это имя compose-сервиса против сгенерированного имени контейнера. Промах здесь означает не ошибку, а тихий no-op: reload «проходит», edge держит старый upstream, все домены 502, и выглядит это как наша поломка. `deploy/scripts/edge-nginx.sh` перебирает известные имена, потом ищет запущенный nginx, который не наш, проверяет конфиг через `nginx -t` и только тогда перезагружает.
- **Smoke-тест переехал на сервер.** Проверка из GitHub-раннера тестировала заодно Cloudflare: bot-challenge раннеру завалил бы заведомо исправный деплой. `deploy/scripts/smoke-test.sh` ходит с самой машины через `curl --resolve`, минуя DNS и CDN, и проверяет то, чем мы владеем — что API отдаёт именно задеплоенный коммит, что Postgres и Redis отвечают, что ни одна SPA не 502-ит. Боевых данных не создаёт: только health-эндпоинты, потому что smoke-тест, оформляющий заказ, отправляет реальный тикет на реальную кухню. Публичная проверка осталась, но переведена в информационную — проблема CDN не должна помечать сборку плохой.
- **Добавлена диагностика `deploy/scripts/server-check.sh`** — только чтение, ничего не перезапускает: чекаут и его чистота, наличие обязательных переменных (имена, не значения), состояние контейнеров, edge, health и коммит в нём, все домены, диск, хвост логов API.
- **`.gitattributes` фиксирует LF** для `*.sh`, конфигов nginx и env-шаблонов. Разработка идёт на Windows, исполнение на Linux, а CRLF в shebang даёт `bad interpreter: /usr/bin/env bash^M` — деплой-скрипт умирает на первой строке по причине, невидимой в диффе.
- **CI начал проверять ветку, которая едет в прод.** `infra/migrate-takeaway-md` не была в триггерах — каждый коммит, доезжавший до клиентов, не проходил ни линтера, ни тестов, ни сборки.

- **Найдено, почему боевой шлюз отвергал наши запросы — две причины подряд.** Первая: без `<KeyInfo>` с нашим сертификатом банк подпись вообще не проверяет, хотя в документированных примерах `<KeyInfo>` нет и опознавать нас он должен по merchantId. Теперь `AGROPROMBANK_INCLUDE_KEYINFO` включён по умолчанию, а сертификат мерчанта стал обязательной настройкой. Вторая, вскрывшаяся сразу за первой: в `<KeyInfo>` уезжал не сертификат, а сертификат вместе с шапкой `Bag Attributes` / `subject=` / `issuer=`, которую `openssl pkcs12 -clcerts` пишет над PEM-блоком — тело сертификата вырезалось «убрать маркеры», а не «взять то, что между ними». Банк отвечал на это жалобой на base64, которая не указывает на причину ни одним словом. Обе починены, вторая закрыта тестом.

- **Сертификат банка для проверки подписи получен без переписки с банком.** В документации про обмен сертификатами одна строка без адреса и ссылки, на сайте их УЦ его нет, в почте тоже. Но подпись под ответом шлюза несёт сертификат подписавшего внутри себя, так что одного безобидного запроса (`tools/agroprombank-fetch-bank-cert.mjs`, проверка заведомо несуществующего токена — денег не двигает, ничего не создаёт) хватило, чтобы забрать его целиком.
- **Добавлен `tools/agroprombank-signature-probe.mjs`** — шлюз отверг нашу подпись, а форму `<Signature>`, которую он ждёт, документация не фиксирует. Скрипт за один прогон отправляет пять вариантов подписи и показывает, на какой банк отвечает про токен, а не про подпись; если отвергнуты все — дело не в XML, и банку надо проверить привязку нашего сертификата к мерчанту.

- **Ключ Агропромбанка теперь реально читается контейнером.** API работает не от root и не от deploy, а от собственного пользователя, так что приватный ключ, положенный на хост с правами 600, был бы ему недоступен — а выглядело бы это как «шлюз не настроен», ровно как при отсутствующем ключе. Uid контейнера зафиксирован (10001), каталог с секретами создаётся с правом на проход, и в `docs/agroprombank-payments.md` записаны точные команды раскладки: конвертация `.pfx` делается на сервере, чтобы приватный ключ существовал в одном месте.

- **Прод переехал на `main`.** `infra/migrate-takeaway-md` была боевой веткой с мая по сентябрь 2026, пока линии были разведены; после того как их свели, держать две ветки стало ровно одним лишним шансом выкатить не то. Триггер деплоя и CI переведены на `main`, чекаут на сервере деплой переводит сам — ручных шагов на машине нет. Старая ветка остаётся только как история и больше ничего не деплоит. Важное следствие для ручного запуска: в выпадающем списке Run workflow теперь нужна та же ветка, что стоит по умолчанию, — на этом промахивались дважды.
- **Автодеплой доведён до зелёного после переезда сервера.** Он не работал с 22 августа, и ломали его четыре разные вещи подряд, каждая пряталась за предыдущей: не заведён секрет с адресом новой машины; не пришпилен её host key; в `DEPLOY_SSH_KEY` лежал ключ от старого сервера, так что новый нас не пускал; и рабочая копия `/opt/takeaway/repo` принадлежала root, из-за чего `git fetch` падал на `cannot lock ref`. Две похожие ошибки ssh — «сервер не тот» и «нас не пускают» — разведены в `deploy/README.md`, потому что читаются они одинаково.

- **Ветка, с которой живёт production, снова совпадает с main.** Линии разошлись 6 мая: на проде ехали `infra/migrate-takeaway-md` (домены takeaway.md, валюта MDL, фикс цен Poster ×100, изоляция заказов для BRAND_ADMIN, роль MENU_EDITOR, карты Leaflet), а в `main` копились M5 и вся работа по подготовке к MVP (синхронизация iiko, возвраты, materialized view аналитики, PDF-чеки, PIN-вход на KDS, соцавторизация, очередь кухни, слоты, налоги, Sentry, PWA, e2e). Три месяца расхождения — это не «потом смержим», а растущая вероятность того, что горячий фикс придётся писать дважды. `main` влит в прод-ветку; миграции обеих сторон сортируются в правильном порядке, так что `migrate deploy` на живой базе доедет без ручных шагов.

### Security

- **Владелец одного бренда видел кухню, заказы и аналитику других брендов.** Скоуп точек выдавал `BRAND_ADMIN` «все точки платформы», поэтому владелец кофейни мог открыть KDS чужой точки, подписаться на её заказы через сокет, назначать курьеров и видеть выручку всей сети на дашборде. Теперь владелец видит только точки своих брендов, менеджер и кухня — только назначенные; проверка стоит во всех маршрутах точки, в KDS-сокете, у курьеров, в доставке и в аналитике. Заодно закрыты запись в чужой бренд через `brandId` в теле запроса и привязка товара к категории другого бренда, а менеджер больше не может выдавать PIN и приглашать сотрудников на точки, к которым не назначен.
- **Токены больше не пишутся в логи API.** Каждая строка лога запроса содержала заголовок `Authorization` целиком — рабочий access-токен клиента или сотрудника — а также cookies; всё это уходило туда же, куда уходят логи. Теперь pino вырезает `authorization`, `cookie`, `stripe-signature` и `set-cookie` до записи, остальная строка остаётся как была.

- **Проверка подписи ответов банка перестала молча пропускать часть трансформаций.** Читалась только первая `<Transform>`, остальные игнорировались — а трансформация, которую проверяющая сторона пропускает вместо того, чтобы применить, это трансформация, которую выбирает атакующий. Боевой шлюз, как выяснилось на первом же реальном ответе, подписывает не так, как написано в документации: за `enveloped-signature` идёт ещё и exclusive c14n. Теперь цепочка проверяется целиком, известные варианты принимаются, любой другой — отказ с указанием причины. Настоящий подписанный ответ боевого шлюза лежит в тестах фикстурой: до этого наш верификатор проверялся только против нашего же подписывальщика, что не ловит ошибку, одинаковую с обеих сторон.

- **CORS перестал отражать любой origin.** Было `origin: true` вместе с `credentials`, то есть страница на любом домене могла обращаться к API от имени залогиненного браузера. Теперь список доменов задаётся `CORS_ALLOWED_ORIGINS`; пустой список оставляет прежнее поведение для локальной разработки, где четыре SPA живут на четырёх портах, но в production пишет в лог предупреждение — это единственное место, где ошибка конфигурации одновременно невидима и эксплуатируема.
- **Swagger в проде выключен по умолчанию** (`SWAGGER_ENABLED`). Он описывает каждый эндпоинт, каждый DTO и требования к авторизации — это готовая карта для того, кто изучает API, поэтому включаться она должна осознанно, а не отключаться.
- **Бэкапы базы шифруются до того, как покидают сервер.** Дамп содержит имена, почты, телефоны и историю заказов, а git-история хранит всё запушенное навсегда, на стороннем хостинге, во всех клонах; удаление файла лишь подчищает рабочее дерево. Это прямо конфликтует с правом на удаление в GDPR и UAE PDPL. Теперь дамп, сжатие и шифрование идут одним пайпом — открытый текст не попадает на диск даже на секунду, — а уничтожение `BACKUP_ENCRYPTION_KEY` делает нечитаемыми все копии сразу. Без ключа скрипт отказывается работать: потерять одну ночь бэкапа поправимо, опубликовать открытую базу клиентов — нет. Пустой результат тоже прерывает выполнение, потому что обрезанный бэкап хуже отсутствующего — он выглядит как настоящий.

### Added

- **Приложение для iOS и Android.** Весь путь клиента нативно, без веба внутри: знакомство, выбор точки на карте или по близости, меню с поиском и быстрым добавлением, конструктор напитка (размер, молоко, добавки), корзина, чекаут «как можно скорее» или ко времени (слоты с учётом загрузки кухни), промокод, подарочная карта, баллы, доставка там, где она включена, оплата привязанной картой Агропромбанка или на месте. Экран заказа живёт от сокета, а без него опрашивает сервер: кольцо обратного отсчёта, шаги, код выдачи с QR, «Я на месте», отмена, повтор заказа, чек на почту. Профиль — лояльность, рефералы, подарочные карты, способы оплаты, уведомления, язык (RU/EN), светлая и тёмная тема. Вход — Telegram (одно касание в приложении Telegram, если оно установлено), Google, Apple на iOS. Цены всегда в валюте точки, а не пользователя. Меню и точки кешируются на устройстве: без сети приложение открывается с последним меню, а не с пустым экраном. Код — `apps/mobile` (Flutter 3.38, Riverpod, go_router), клиент API — `libs/api-client-dart`; сборка, ключи и выпуск в сторы — в `apps/mobile/README.md`.
- **Пуши в мобильное приложение.** FCM-провайдер был заглушкой; теперь он отправляет через FCM HTTP v1 на Android и iOS (APNs — через Firebase), группирует уведомления по заказу и сам вычищает токены, которые Firebase объявил недействительными. Включается переменными `FIREBASE_PROJECT_ID` / `FIREBASE_CLIENT_EMAIL` / `FIREBASE_PRIVATE_KEY` сервис-аккаунта; пока они пусты, всё работает как раньше.
- **Вход через Telegram Login — новый официальный протокол Telegram.** Telegram перевёл вход на OpenID Connect (core.telegram.org/bots/telegram-login): вместо подписанного HMAC-ом набора полей клиент получает ID-токен, подписанный ключами Telegram. API принимает его на `POST /auth/telegram/oidc` и проверяет так же строго, как Google и Apple: подпись по JWKS Telegram (RS256 или ES256 — что выбрано у бота), издатель, наш client id, срок. Аккаунт находится по тому же Telegram id, что в Mini App и старом виджете, — у клиента остаётся один профиль. В приложении поток написан по образцу официальных SDK Telegram: если Telegram установлен, вход подтверждается в нём одним касанием, иначе открывается страница Telegram; код меняется на токен по PKCE, секретов в приложении нет. Веб и привязка Telegram в админке переходят на новую библиотеку Telegram, как только в `index.html` задан `__TELEGRAM_CLIENT_ID`, — до этого работает прежний виджет, так что выкладка ничего не ломает. Заодно заблокированный пользователь больше не может войти через Telegram: Google и Apple его уже отсекали, Telegram выдавал сессию.
- **`GET /auth/telegram/config`** отдаёт публичные id бота, его username и client id для Telegram Login. Зашивать их в сборку приложения значило бы выпускать новую версию в сторы при каждой смене бота.

- **Бизнес подключается сам — от регистрации до первого заказа.** Регистрация в админке сразу спрашивает валюту бренда (MDL по умолчанию) и проверяет телефон; вместо «такой email уже есть» на любую коллизию — точная причина. После регистрации владелец попадает на дашборд с чек-листом «Запуск бренда» (логотип, точка с адресом и часами, меню с фото, оплата, модерация), а на каждой странице видит, где бренд в модерации. Модератор отклоняет в окне с обязательной причиной, владелец получает письмо, исправляет и отправляет повторно одной кнопкой; одобрение, отказ и новые заявки приходят письмами (владельцу — на языке бренда) и в ops-чат. У бренда в настройках появились валюта (до первого заказа) и язык, в меню «Бренды» — счётчик заявок. Контакт поддержки для отклонённых брендов задаётся `SUPPORT_EMAIL` / `SUPPORT_TELEGRAM`.
- **Меню можно собрать без инструкции.** У товара появились фото (до шести, первое — главное, видно на сайте и в Mini App), цена вводится в леях, а не в копейках, время — в минутах, подписи полей больше не исчезают. Размеры, молоко и добавки редактируются прямо в строке, типы подписаны по-русски, адреса товаров и опций генерируются из русских названий сами. Товар можно снять с продажи на конкретной точке — до отмены или до конца дня, категории и товары — упорядочить стрелками. Удаление категории с товарами предлагает перенести их, а удаление товара больше не падает с 500 из-за корзин покупателей. В карточку товара добавлены описание, КБЖУ, кофеин, диетические метки и аллергены.
- **Точка открывается, только когда готова принимать заказы.** Новая точка создаётся закрытой и показывает чек-лист: место на карте, часовой пояс, часы работы, товары в меню, одобрение бренда. Часовой пояс выбирается из списка с поиском (по умолчанию — Кишинёв) и проверяется сервером, валюта берётся из бренда и блокируется после первого заказа. Редактор часов различает «круглосуточно» и «по расписанию», выходные по дням и окна через полночь; в «Кассе и кухне» — налог, способы получения, время приготовления, лимиты заказов и минимальная сумма в валюте; есть фото точки и доступ на кухню с PIN сотрудников. Точку с заказами нельзя удалить — только закрыть.
- **Бариста видит, что именно заказали.** Размер, молоко, добавки и пожелание покупателя теперь сохраняются в заказе и показываются на кухонном экране, в карточке заказа в админке, в письме и PDF-чеке и на экране заказа у клиента на сайте и в Mini App. Раньше «латте L на овсяном с ванилью» приходил на кухню как «1× Латте».
- **Деньги списываются, когда точка берёт заказ в работу, а не в момент оформления.** Раньше карта дебетовалась на чекауте, и клиент, чей заказ точка так и не приняла, ждал возврата за то, чего не получил. Теперь на чекауте сумма **бронируется** (преавторизация, которую схема банка поддерживает), а списывается она в тот момент, когда сотрудник нажимает «Принять» на кухонном экране. Отказ банка в этот момент не даёт принять заказ — иначе кухня начала бы готовить неоплаченное. Отмена заказа клиентом снимает бронь: замороженные деньги возвращаются сразу, а не по истечении срока холда на стороне банка. Поведение переключается настройкой `AGROPROMBANK_HOLD_UNTIL_ACCEPTED` — для мерчанта, у которого в договоре эквайринга нет преавторизации.
- **Клиент видит, что с его деньгами.** Экран заказа открывался сразу с обратным отсчётом, и подтверждения оплаты в нём не было ни в каком виде — заплатил человек или нет, приходилось угадывать. Теперь первым блоком идёт состояние платежа: «Оплата прошла», «Деньги забронированы» с пояснением, когда их спишут, «Оплата не прошла» или «Оплата на месте», с суммой и маской карты. То же самое в Telegram-приложении. Состояние приходит с сервера вместе с заказом, а не выводится из его статуса, поэтому бронь не выглядит как оплата.
- **Оплата картой появилась в вебе, не только в Telegram-приложении.** «Способы оплаты» в профиле были заглушкой со словами про форму Stripe и «скоро в v1.5» — притом что привязка карт уже работала в мини-аппе, а Stripe в Приднестровье не работает вовсе. Страница стала рабочей: привязка карты в два шага, список карт, выбор основной, удаление. На чекауте появился настоящий выбор — привязанная карта или оплата на месте; вместо кнопок «Pay» и «G Pay», которые не были подключены ни к чему и создавали впечатление, что заказ оплачен.

- **Оплата картой через Агропромбанк («Клевер»).** Stripe в Приднестровье не работает, а заказ без оплаты — это очередь на кассе, ради ухода от которой продукт и существует. Клиент привязывает карту один раз: последние четыре цифры, телефон, банк-эмитент и одноразовый пароль из SMS, — после чего каждое следующее списание идёт по непрозрачному токену без его участия, и оплата в Telegram-приложении умещается в одно нажатие. Данные карты на наши серверы не попадают вовсе, а токен, хотя и не содержит номера, сам по себе разрешает списание, поэтому лежит в базе зашифрованным. Всё общение с банком — только с сервера: приватный ключ мерчанта в браузере или в мобильном приложении означал бы его компрометацию. Три правила определяют поведение с деньгами: номер счёта выделяется до звонка в банк и никогда не переиспользуется, обрыв связи оставляет платёж в `PENDING` (карта могла быть списана, и пометить такой платёж неудачным — значит отдать заказ бесплатно), а в `PAID` заказ переводит только ответ с проверенной подписью. Расхождения добирает сверка раз в пять минут. Возвраты, отмены и списание преавторизации доступны из админки. Пока банк не выдал сертификат, всё это проверяется на встроенной песочнице, которая говорит на том же протоколе и проверяет нашу подпись, — тот же код обслуживает и тесты, и локальный мок, и изолированный docker-стек, так что разойтись они не могут.

- **Сквозной e2e на путь клиента.** Раньше проверялось, что отдельные экраны рисуются; поймать, что два экрана не разговаривают друг с другом, было нечем — а именно там и живут интересные баги. Новый набор прогоняет настоящее Angular-приложение по всему пути: точка → меню → товар → корзина → чекаут → выбор окна → заказ → экран статуса, и проверяет не только то, что нарисовано, но и что чекаут реально отправил (`SCHEDULED` с настоящим слотом, ASAP без времени, `pointsToSpend`). API подменён на **stateful**-заглушку: добавление в корзину действительно меняет сумму на чекауте, а набор статичных фикстур проходил бы и при неработающей связке экранов. Postgres и Redis не нужны, так что набор идёт в CI отдельным джобом. Платёж намеренно не покрыт — провайдера меняем.

### Fixed

- **Цена на кассе больше не расходится с меню.** Корзина хранила цену на момент добавления: исправленная цена, скрытый товар или удалённый вариант на неё не влияли. Теперь при оформлении корзина пересчитывается по текущему меню; если что-то изменилось, заказ не создаётся, покупатель видит «Цены или состав меню изменились — проверьте корзину», а корзина уже обновлена. Сервер сам следит за правилами опций: не больше одного размера, неизвестный вариант отклоняется, без выбора ставится вариант по умолчанию.
- **Товар открывался у другой кофейни.** Адреса товаров уникальны только внутри бренда, а теперь генерируются из названий, поэтому у двух кофеен оба «латте» — `/products/latte`. Сайт и Mini App передают точку, в меню которой находится покупатель, и товар ищется в её бренде.
- **Кухонный экран открывался на чужой точке.** Доска показывала все точки платформы и открывала первую — после сужения прав владельца это чаще всего была точка другого бренда и ошибка вместо заказов. Теперь в списке только точки пользователя, и доска открывается на той, для которой настроен планшет.
- **Загрузка картинок снова работает.** API работает на Fastify, где загрузчик файлов из Express не видит файл, поэтому логотип бренда возвращал 415 на любую картинку. Загрузка переписана под Fastify; тип файла определяется по содержимому (JPEG, PNG, WebP, AVIF до 5 МБ), SVG не принимается — он может нести скрипт.
- **Адреса из русских названий.** Слаги собирались только из латиницы: «Ванильный сироп» давал пустую строку и ошибку сохранения, «Кофейня Ромашка» — случайный набор символов. Теперь кириллица транслитерируется: `vanilnyy-sirop`, `kofeynya-romashka`.
- **Живые обновления снова работают в вебе, Mini App, на кухонном экране и в диспетчерской.** Все четыре приложения подключают сокет к своему же домену, а Socket.IO ведёт рукопожатие через `/socket.io/` — мимо `/api`, которое единственное проксировалось на API. Запрос падал в fallback SPA и получал в ответ `index.html`: статус заказа у клиента не двигался сам, новые заказы на KDS появлялись только после перезагрузки страницы, диспетчерская тоже стояла. Nginx теперь проксирует `/socket.io/` на всех SPA-доменах (с апгрейдом до WebSocket и таймаутом, рассчитанным на смену у кухонного экрана), dev-прокси всех четырёх приложений — тоже.
- **После закрытия точки «Сейчас» больше не предлагается.** Часы работы проверялись только в момент создания заказа: клиент в 23:40 выбирал «Сейчас», проходил весь чекаут и получал голое «The store is closed at that time». Статус точки при этом оставался «открыто» — его переключают руками, а часы никто, кроме заказа, не смотрел. Теперь API отдаёт у точки `openNow` — примет ли она ASAP-заказ прямо сейчас, по тем же часам и в том же часовом поясе, что и проверка заказа, с учётом того, что заказ будет готов через текущий ETA. Веб и Mini App по нему выключают «Сейчас», объясняют почему и сразу открывают ближайшие свободные окна.
- **Цены в карточке товара и на чекауте — в валюте точки.** В вебе и в Mini App они были зашиты в USD (а веб-чекаут брал валюту из профиля клиента), так что латте за 20 леев показывался как «$20.00», и сумма на кнопке оплаты не совпадала с тем, что спишут. Меню и история заказов валюту точки брали и раньше.
- **Ссылка «Привязать карту» на веб-чекауте вела в пустоту** — на `/profile/payment`, которого нет; страница способов оплаты живёт на `/profile/payment-methods`.
- **Фото товаров из Poster снова видны.** Poster отдаёт фото относительными путями (`/upload/pos_cdb_…/menu/product_….jpeg`), и импорт меню сохранял их как есть. Браузер и мобильное приложение достраивали такой путь до своего домена, takeaway.md отвечал страницей SPA — и все 111 фото NoName Coffee были битыми в вебе и в Mini App. Импорт теперь пишет абсолютные ссылки на joinposter.com (http-ссылки Poster заодно переводятся на https), а миграция чинит уже сохранённые товары: трогает только пути `/upload/…`, порядок фото сохраняет.

- **Формы в админке обрезались краем карточки.** У поля ввода есть собственная ширина — около 180 пикселей, — и ни колонка сетки, ни элемент flex не сжимаются уже того, что внутри них. Поэтому два поля рядом в узкой карточке раздвигали строку шире карточки, а не вставали друг под друга: при редактировании точки пропадала вся правая половина формы — страна, email, долгота. Теперь элементы управления не держат минимальную ширину, строка полей переносится, когда места нет, а карточка точки на время редактирования занимает всю ширину списка. На странице меню горизонтальная прокрутка уехала с колонки на саму таблицу: раньше широкая таблица утаскивала вбок всю колонку вместе с формой товара, и форма уходила за левый край. Добавлен набор проверок, который открывает каждую форму добавления и редактирования на четырнадцати страницах админки при двух ширинах окна и падает, если хоть одно поле не помещается.

- **API отдавал свою внутреннюю поломку вместо настоящей ошибки.** Глобальный фильтр ошибок собирался вручную в `main.ts`, без http-адаптера: `BaseExceptionFilter` получает его только через DI, а без него падал сам, на каждой ошибке. В итоге любой ответ с ошибкой — валидация, 401, 404, конфликт слага, 500 — приходил клиенту как 500 с текстом «Cannot read properties of undefined (reading 'isHeadersSent')». Сломано с момента подключения Sentry, и ломало все четыре приложения разом: на экране всегда была эта строка вместо причины, так что ни один сбой нельзя было понять по сообщению. Теперь адаптер обязателен в конструкторе — повторить ошибку не даст компилятор, — а поведение закреплено тестом на настоящем Fastify-приложении. Отдельное следствие, которое из-за этого же не работало: молчаливое продление сессии срабатывает только на 401, а 401 не доходил, — поэтому через пятнадцать минут жизни токена админка начинала сыпать ошибками на каждом запросе до ручного перелогина. Перехватчик менять не пришлось, он просто снова работает; путь, который месяц был мёртвым, закрыт тестами.

- **Товар добавлялся в корзину точки чужого бренда.** Страница товара открывается по своему адресу и точки в нём нет, поэтому веб брал первую точку каталога — а он отсортирован по расстоянию и времени ожидания, по всем брендам сразу. Пока бренд был один, это работало; со вторым брендом «Добавить в корзину» начало упираться в отказ сервера «товар не принадлежит бренду этой точки». Теперь товар знает свой бренд, и обе витрины выбирают точку этого же бренда: в Telegram-приложении та, что открыл покупатель, если она подходит, иначе любая подходящая. Если ни одна точка бренда сейчас не принимает заказы, так и написано, вместо отказа при нажатии.

- **Точку и меню снова можно создать, а «У пользователя нет бренда» больше не прячет настоящую причину.** Точки, категории, товары и промо создаются внутри бренда, и админка брала его из общего контекста — но когда список брендов не приходил, контекст оказывался пустым, и разницу между «бренда действительно нет» и «список не загрузился» никто не хранил. Любой сбой запроса — истёкшая сессия, 403, 500, обрыв связи — выглядел одинаково: сухое «У пользователя нет бренда» на форме точки и, на странице меню, кнопки, которые просто ничего не делают. Теперь причина сохраняется и показывается словами банка ошибки, рядом с кнопкой «Повторить», а страница меню про свою беду больше не молчит.

- **Первый бренд можно завести прямо из админки.** На свежей установке брендов нет вовсе: супер-админ попадал в тупик, где точку создать нельзя из-за отсутствия бренда, а бренд — неоткуда, потому что страница «Бренды» была только очередью модерации, а создание существовало лишь в API. На ней появилась форма нового бренда; созданный супер-админом бренд сразу одобрен (модератор — он сам) и сразу становится рабочим контекстом, так что точки и меню доступны без перезахода.

- **Страница меню слушается переключателя брендов.** Она запрашивала список брендов сама и молча брала первый, игнорируя выбор в верхней панели: супер-админ с несколькими брендами, переключившись, продолжал править меню первого по алфавиту — и видел это только по результату. Теперь меню работает в том же контексте, что точки и промо, и перезагружается при смене бренда.

- **Настройки бренда перестали отдавать 403 супер-админу.** Раздел есть в его меню, а эндпоинт был доступен только владельцу бренда, так что страница открывалась пустой ошибкой. Теперь супер-админ редактирует тот бренд, на котором стоит переключатель; владельцу бренда по-прежнему достаётся только свой, что бы ни пришло в запросе.

- **Smoke-тесты были сломаны с момента перехода на i18n** и никто этого не видел: CI гоняет `lint`/`test`/`build`, но никогда `e2e`. Приложение по умолчанию русское, а проверки написаны на английских строках. Локаль теперь закрепляется явно, так что набор не зависит от того, каким станет дефолт. Заодно поправлена проверка страницы входа: она всё ещё искала форму телефона, которой нет с M1.

- **Баллами теперь можно платить.** Программа лояльности умела только копить: `debit()` в сервисе был, но единственным клиентским эндпоинтом оставался `GET /loyalty/me`, и баланс мог расти вечно, ни разу ничего не дав. Балл стоит 1 цент — вместе со ставкой начисления это ровно 1% возврата, намеренно скромно: баллы это повод вернуться, а не скидочная схема, и щедрый курс почти невозможно отыграть назад, когда клиенты уже накопили балансы. Минимум к списанию — 100 баллов, сжигать девять баллов ради девяти центов не стоит ничьего внимания. Новый `POST /loyalty/redeem/quote` считает, сколько реально можно списать: запрошенное зажимается балансом и стоимостью заказа, чтобы баллы никогда не превратились в возврат наличными. Клиенту нельзя верить, поэтому тот же расчёт повторяется при создании заказа, а списание идёт внутри той же транзакции. Баллы вычитаются как **скидка**, а не как оплата: продавец снижает цену, значит уменьшается и налоговая база — в отличие от подарочной карты, которая куплена за деньги и лишь погашает счёт. При отмене и экспирации заказа баллы возвращаются, но **не** в lifetime: иначе клиент поднимал бы себе уровень циклом «заказать — отменить».

- **Web стал настоящим PWA.** «Web/PWA» было заявлено в брифе с самого начала, а на деле существовал только `sw.js` для пушей: манифеста, иконок и офлайн-оболочки не было, на домашний экран приложение не ставилось. Добавлены манифест с ярлыками «Мои заказы» и «Точки рядом», иконки 192/512 плюс отдельные maskable-версии (Android обрезает иконку в круг, и содержимое должно уложиться в 40% холста, а не в 80%), apple-touch-icon и мета-теги для iOS, который манифест игнорирует. Service worker регистрируется при старте, а не только когда клиент включит уведомления — иначе офлайн-оболочка была бы у того меньшинства, кто согласился на пуши. Кэшируется намеренно мало: оболочка и иконки; ответы API не кэшируются никогда, потому что устаревший ETA или статус заказа хуже честной ошибки — весь продукт это обещание про время.

### Fixed

- **nginx: две ловушки, из-за которых PWA бы не работал.** `sw.js` попадал под правило годового `immutable`-кэша для `.js` — браузер навсегда запомнил бы первую увиденную версию воркера, и ни один деплой не смог бы её заменить. А `.webmanifest` нет в стандартном `mime.types` nginx, и манифест, отданный как `text/plain`, просто игнорируется: предложение установить приложение молча не появляется.
- Бейдж «Coffeepass» на главной обещал подписку, которой нет ни в схеме, ни в API. Раздел переименован в «Баллы» / «Rewards» — это описывает программу лояльности, которая действительно работает.

- **PIN-локскрин в KDS.** Бэкенд PIN-входа был готов с M5, экрана не было — бариста вводил рабочий email и восьмизначный пароль на планшете, стоящем на выдаче в зоне видимости очереди. Теперь вход по PIN — способ по умолчанию, с крупной цифровой клавиатурой под планшет (а не текстовым полем: собственная клавиатура устройства закрывает пол-экрана, а у бариста часто занята одна рука). Точка выбирается один раз и запоминается; вход по email остался для менеджеров одной ссылкой ниже.
- **Карточка заказа в админке и возврат из интерфейса.** Эндпоинт возврата существовал с M5, и дотянуться до него было нечем: менеджер напротив недовольного клиента не имел ни одной кнопки. Новый `GET /admin/orders/:id` отдаёт состав, платежи, уже возвращённые суммы и полную ленту событий; RBAC тот же, что у списка, и заказ чужой точки отвечает 404, а не 403 — подтверждать существование заказа в недоступной точке само по себе утечка. Панель по клику на строку: сумма возврата предзаполняется всем возвращаемым остатком (частичный возврат — исключение), причина и комментарий уходят в аудит-лог, действие подтверждается отдельно, потому что необратимо.

- **`GET /api/health/ready` — проба, которая действительно что-то проверяет.** Старый `/api/health` отвечал «процесс жив» и оставался зелёным при лежащем Postgres, то есть деплой-гейт пропускал релиз, не способный обслужить ни одного заказа. Новая проба ходит в Postgres и Redis, каждая с таймаутом в 2 секунды (зависшее соединение обязано быстро сказать «я мёртв», иначе оркестратор не сможет нас перезапустить), и отдаёт 503, если хоть что-то недоступно. Деплой-воркфлоу переключён на неё.
- **Операционные алерты в Telegram.** Раньше алертов не было вообще: мёртвый Redis, планшет KDS, в который никто не залогинился, переставшая обновляться materialized view — всё это было тихо, пока кто-нибудь не догадается посмотреть. Раз в 5 минут проверяются три вещи, которые стоят реальных заказов: недоступная зависимость, оплаченные заказы, не принятые кухней дольше 10 минут, и отставшая аналитика. Дедупликация через Redis — двухчасовая авария шлёт одно сообщение, а не сто двадцать; после устранения мьют снимается, чтобы повтор снова разбудил. Пустой `OPS_ALERT_TELEGRAM_CHAT_ID` полностью выключает алертинг.
- **Sentry на API и всех четырёх SPA.** Единственным следом продакшн-ошибки была строчка в stdout контейнера. На бэке инициализация вынесена в отдельный `instrument.ts`, импортируемый первым — Sentry патчит HTTP и драйверы БД во время require, и любой модуль, загруженный раньше, остался бы непропатченным. Nest ловит все исключения своим слоем, поэтому добавлен фильтр, который репортит только настоящие сбои: 400 за неверный промокод — это система работает, и такие события похоронили бы единственную реальную 500-ку. Чувствительные заголовки (`Authorization`, `stripe-signature`, cookies) и тела запросов вырезаются, на фронте из URL вырезается query string — там ездят QR-токен заказа и токен сброса пароля. DSN задаётся в `index.html` как остальная runtime-конфигурация; пустой DSN — полный no-op, нормальное состояние для локальной разработки и CI. `extract-spa.sh` проставляет версию сборки в `window.__BUILD_VERSION`, чтобы issue указывал на конкретный деплой.

- **Налог считается, а не стоит нулём.** `taxCents` был захардкожен `0`, из-за чего чек в любой стране с НДС был юридически неверным, а выручка в аналитике завышена на неотделённый налог. У точки появились `taxRateBps` (базисные пункты: 500 = 5% для ОАЭ, 2000 = 20% для Великобритании) и `taxIncludedInPrice`. Второй флаг важнее, чем кажется: в ОАЭ, Великобритании и ЕС розничная цена налог **уже содержит** и он выделяется из неё для чека, а в большинстве штатов США добавляется на кассе — это меняет сумму к оплате, а не только строку в чеке. База налога — сумма позиций за вычетом промо-скидки плюс доставка; подарочная карта вычитается **после**, потому что это способ оплаты, а не скидка, и оплата картой не делает продажу необлагаемой. Налог отдельной строкой в письме и PDF-чеке, с разной формулировкой для «в том числе» и «сверху». Функция вынесена в `@takeaway/utils` и используется и сервером, и обоими чекаутами — иначе точка с налогом сверху показывала бы 20.00, а списывала 21.75.

- **Брошенные заказы больше не копятся вечно и возвращают то, что держали.** Статус `EXPIRED` был в перечислении с самого начала, но выставлять его было некому — и такие заказы не были безобидными: каждый держал промокод против лимита «одно применение на клиента», держал списанные с подарочной карты деньги и занимал окно выдачи, которое точка могла продать тому, кто действительно придёт. Раз в минуту неоплаченные заказы старше `ORDER_PAYMENT_TTL_MINUTES` (по умолчанию 15, значения ниже 5 подтягиваются вверх) переводятся в `EXPIRED`, промокод и остаток гифт-карты возвращаются в той же транзакции, заказ снимается с кухонного экрана, клиенту уходит пуш. Статус перечитывается внутри транзакции: если оплата пришла между выборкой и обработкой, заказ остаётся у клиента.
- **Отмена заказа тоже возвращает промокод и подарочную карту.** Ровно та же дыра: и то и другое списывалось при создании заказа, а `cancel` их не трогал — клиент терял и купон, и деньги на карте.

- **Часы работы точки теперь применяются, а не только редактируются.** `StoreWorkingHour` лежал в базе с самого начала и не проверялся нигде: заказ на 3 часа ночи спокойно уходил на кухонный экран. Проверка идёт в таймзоне точки через `Intl` — не через фиксированный сдвиг, который ломается дважды в год, — и понимает ночные смены (22:00–02:00 покрывает и пятницу 23:30, и субботу 01:00). Точка без заполненного расписания считается работающей круглосуточно: это состояние, в котором точка заводится, и отказывать в заказах из-за незаполненной формы было бы хуже. Закрытые окна выдачи просто не предлагаются на чекауте — вычеркнутое 03:00 это шум, а вот занятое 08:15 это информация.
- **Стоп-лист блокирует заказ, а не только подсвечивает карточку.** Раньше `onStopList` был подсказкой для витрины, и ничто не мешало устаревшему экрану, диплинку или прямому вызову API отправить снятую с продажи позицию на кухню. Теперь проверка стоит на добавлении в корзину, на изменении позиции и ещё раз при создании заказа — товар может попасть в стоп-лист между наполнением корзины и оплатой. Записи с истёкшим `expiresAt` не блокируют: они уже автоматически вернулись в продажу.

- **ETA считается от фактической очереди кухни, а не от статичного поля.** Раньше `Store.currentEtaSeconds` никто не пересчитывал: двадцать заказов в 8:40 получали то же обещание, что один заказ в 15:00. Теперь `eta = базовая накладная точки + невыполненная работа / параллелизм кухни + время своей позиции`. Поле переименовано в `baseEtaSeconds` — это честно описывает, чем оно было. У заказа появились два разных числа: `prepSeconds` (сколько ждёт клиент — самая долгая позиция, бариста тянет шот пока взбивается молоко) и `workSeconds` (сколько заказ занимает кухню — сумма по позициям); заказ из четырёх напитков грузит бар вчетверо сильнее, чем заставляет ждать своего клиента. Заказ в работе считается наполовину сделанным. Витрина и карточка точки отдают живое `currentEtaSeconds`, список точек — одним групповым запросом, а не запросом на пин.
- **Слоты выдачи по 15 минут.** У точки есть `slotCapacity` — сколько выдач она готова пообещать в одном окне. Переполненное окно перестаёт предлагаться. Новый публичный `GET /stores/:id/pickup-slots` отдаёт двенадцать часов вперёд, занятые окна приходят помеченными, а не пропадают: вычеркнутое 08:15 читается как «загруженное утро», исчезнувшее — как баг. Чекаут в web и TMA больше не показывает свободное поле времени — только окна, которые точка успевает обслужить. Вместимость проверяется и на создании заказа, включая ASAP: без этого час пик просто растягивал бы всем ETA, ради чего вся модель и делалась. Настройки `baseEtaSeconds` / `kitchenParallelism` / `slotCapacity` доступны в админке.

- **Вход через Google и Apple** для клиентов, рядом с Telegram. На экране входа web три провайдера: Google (официальная кнопка Google Identity Services), Apple (кнопка по Apple HIG) и Telegram-виджет под разделителем. Любой можно не включать — пустой client id в `index.html` прячет кнопку, при пустых всех трёх показывается явное «способ входа не настроен». Сервер проверяет ID-токен по JWKS провайдера: RS256 с зафиксированным алгоритмом (заголовку `alg` не доверяем), `iss`, `aud` против собственных client id, `exp`; ключи кешируются на час и переживают ротацию. Аккаунт с **подтверждённым** email привязывается к существующему клиенту, так что человек, начавший в Telegram, попадает в тот же профиль с той же историей заказов; staff-аккаунты для такой привязки закрыты. Новые переменные окружения: `GOOGLE_OAUTH_CLIENT_IDS`, `APPLE_OAUTH_CLIENT_IDS` (списки через запятую — по одному client id на платформу, с прицелом на Flutter).
- **Telegram Mini App: вход убран полностью.** Сессия выпускается из `initData` в app-initializer, до первого рендера, поэтому ни один экран не успевает уйти в запрос без токена. На 401 интерсептор молча ротирует refresh-токен, а если тот недействителен — пересоздаёт сессию из того же `initData` и повторяет запрос: чекаут, открытый через полчаса после запуска бота, просто работает. Route guard даёт повторную попытку, если API был недоступен на старте. Экраны «войдите, чтобы увидеть заказы» и «войдите, чтобы добавить в корзину» заменены на честное «нет связи с сервером» — внутри Telegram неавторизованность может быть только технической.
- **Build version visibility** во всех артефактах. `deploy.sh` вычисляет триплет `version` (`git describe --tags --always --dirty`) / `commit` (full SHA) / `builtAt` (UTC ISO) на каждом деплое. API возвращает их в `GET /api/health`. Каждая SPA получает `/version.json` от `extract-spa.sh` и показывает короткий бейдж в правом нижнем углу через `lib-version-badge` (`libs/ui-kit`); по клику триплет копируется в clipboard. Скрытие через `?no-version` в URL — для скриншотов.
- **iiko Cloud sync (M5)**: parity with Poster. `/api/1/nomenclature` для menu import, `/api/1/stop_lists` для periodic poller (30 мин cron), `/api/1/order/create` для outgoing orders. Provider требует pinned `settings.organizationId` для menu и orders. Inline product modifiers переносятся как `Modifier` rows. См. обновлённый `docs/integrations.md`.
- **Stripe refund flow в admin**: `POST /admin/orders/:id/refund` — full или partial возврат. Optimistically обновляет `Payment.refundedCents`/`PaymentStatus`, эмитит `REFUND_ISSUED` event с `actorId`. RBAC: SUPER_ADMIN видит всё, BRAND_ADMIN — только свои бренды, STORE_MANAGER — только свои store-scope.
- **Analytics на materialized view**: миграция создаёт `mv_orders_daily` (per-(brand, store, day) роллап с `orderCount`, `revenueCents`, `slaHits/Total`, `pickupSecSum/Count`). `AnalyticsRefreshService` каждые 5 минут делает `REFRESH MATERIALIZED VIEW CONCURRENTLY`. Endpoints `dashboardSummary`, `revenueSeries`, `storePerformance` теперь читают MV вместо raw `Order` сканов; `topProducts`/`cohort` пока остались на live tables и помечены как кандидаты на следующий MV.
- **PDF receipt**: чек прикладывается PDF-аттачментом к welcome/receipt письму через `pdfkit` (built-in Helvetica). Для receipt с non-ASCII (Cyrillic и др.) PDF не генерируется — идёт только HTML, чтобы не плодить broken glyphs. Customer может повторно запросить чек: `POST /me/orders/:id/resend-receipt`. Зависимости: `pdfkit` ^0.15, `@types/pdfkit`. Только в API контейнере (Angular bundles не задеты).
- **KDS PIN auth (API)**: 4–6 цифр на staff-юзера, scoped to one store. Endpoints — `POST /auth/kds/pin` (login), `PUT/DELETE /admin/stores/:id/staff/:userId/kds-pin` (admin set/clear). PIN хранится как `HMAC-SHA256(storeId|pin)` с key `KDS_PIN_SECRET` — O(1) lookup без bcrypt. Per-store unique enforced partial index. UI lockscreen в `apps/kds` — отдельный заход.
- **M6 Flutter kickoff**: scaffold `apps/mobile/` с `pubspec.yaml` (Riverpod, go_router, Dio + Retrofit, Hive, flutter_secure_storage, socket_io_client, firebase_messaging, sign_in_with_apple, google_sign_in, flutter_stripe, mapbox_gl, qr_flutter), минимальный `lib/main.dart`, README с PR-разбивкой M6 PR1–PR8. До `flutter create` собирать нечем — это первый шаг по PR1.
